# 2026-04-30 M104 방향 제언: 교정 이력 UX 강화 및 가시성 완결 (Gemini)

## 1. 개요
M98에서 '교정 이력 상세 조회'가 도입된 이후, M102-M103을 통해 선호도 관리 기능(삭제, 신뢰도 토글)이 보강되었습니다. M104에서는 선호도의 근거가 되는 교정 데이터에 대한 접근성을 근본적으로 개선하는 '교정 이력 UX 강화(Correction History UX Enhancement)'를 제언합니다.

## 2. 조사 및 판단

### 2.1. 현재 구현의 한계
- **데이터 병목:** 백엔드 핸들러(`get_correction_list`)가 `limit=5`로 하드코딩되어 있으며, 프런트엔드 UI(`PreferencePanel.tsx`)는 이를 다시 `slice(0, 3)`으로 제한하여 보여주고 있습니다.
- **검색 및 필터 부재:** 검색 입력창은 존재하나 상태(status)별 필터링 기능이 UI에 노출되지 않아, 교정이 쌓일수록 특정 이력을 찾기 어려운 구조입니다.
- **가시성 단절:** M98 상세 조회가 구현되었음에도 불구하고, 정작 리스트가 극도로 제한되어 있어 사용자가 시스템의 학습 근거를 충분히 검토하기 어렵습니다.

### 2.2. 후보군 비교
- **후보 A (선호 내용 편집):** 선호도 패턴(corrected_text)을 직접 수정하는 기능입니다. 하지만 패턴 수정 시 `delta_fingerprint`가 변경되어야 하므로 구현 복잡도가 높고, 잘못 수정할 경우 재사용 정합성이 깨질 위험이 있습니다.
- **후보 B (교정 이력 UX 강화):** 기존 API의 잠재력을 끌어올리는 저위험 고가치 작업입니다. (선정)

## 3. 권고 (Recommendation)

**RECOMMEND: implement Correction History UX Enhancement (Choice B)**

### 기술/제품적 이유:
1. **Evidence Visibility 아크의 완결:** M98(상세)이 '깊이'를 제공했다면, M104(리스트/필터)는 '너비'를 제공합니다. 사용자가 전체 교정 흐름을 한눈에 파악하고 필터링할 수 있게 함으로써 제품의 투명성을 완성합니다.
2. **저비용 고효율:** 백엔드 스토어 계층은 이미 필터링과 리밋을 지원합니다. 핸들러와 웹 라우터의 파라미터 전달 체계만 정비하면 즉시 효과를 볼 수 있습니다.
3. **선호도 관리의 전제 조건:** 선호도를 삭제(M102)하거나 신뢰도를 조정(M103)하기 전에, 사용자는 근거가 되는 교정 이력을 충분히 찾아볼 수 있어야 합니다.

### 실행 가이드:
- **Backend:** `app/web.py`에서 `limit`, `offset`(또는 `status`) 쿼리 파라미터를 추출하여 `get_correction_list`에 전달. 핸들러의 하드코딩된 `limit=5` 제거.
- **Frontend:** `PreferencePanel.tsx`에서 `slice(0, 3)` 제한을 해제하고, '더 보기(See More)' 또는 간단한 페이지네이션/필터 탭 UI 추가.
- **Branch:** `fix/m103-preference-reliability` 베이스에서 `feat/m104-correction-history-ux` 생성.
